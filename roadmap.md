# ARDOR: План опрессовки

**Статус:** Draft for approval  
**Дата:** 2026-09-03  
**Предлагаемое название раздела:** `План опрессовки` / `Pressure Test Plan` / `Painekoesuunnitelma`

## 1. Цель

Раздел хранит независимые списки труб, которые ещё нужно опрессовать. Пользователь вставляет номера построчно, например:

```text
122355/1
123561/12
```

ARDOR автоматически группирует строки по bundle, показывает трубу серой, пока она не найдена в завершённом активном логе, и зелёной, когда точный номер трубы присутствует в основной ревизии активного лога. Нажатие на зелёную трубу открывает карточку найденного лога.

Этот раздел не создаёт Pressure Test, не изменяет CSV, ревизии, PTR или PipeCloud. Он использует их как источник фактического статуса.

## 2. Пользовательский сценарий

1. Пользователь открывает вкладку `План опрессовки`.
2. Создаёт список с названием, например `NB1402PM / Zone 3`.
3. Вставляет номера труб по одному на строку, через запятую или целиком копирует выделенные строки таблицы PipeCloud.
4. При вставке PipeCloud ARDOR извлекает только номера после `Fit`, сохраняет исходную строку и доступные колонки PipeCloud; эти колонки не влияют на статус готовности.
5. ARDOR нормализует пробелы, проверяет формат `bundle/pipe` и предупреждает о дублях в этом списке.
6. Список отображается группами: Bundle `122355`, Bundle `123561` и далее; внутри группы трубы сортируются по номеру после `/`: `1`, `2`, `12`.
7. Пока точный номер отсутствует среди `Pipe` активной primary revision, строка серая и имеет статус `Ожидает опрессовки`.
8. Когда оператор завершает обычный лог с той же трубой, после обновления списка строка автоматически становится зелёной, показывает `Log No.` и доступна как ссылка.
9. Нажатие на зелёную строку открывает уже существующий `TestDetailModal` этого лога. Для нескольких совпадений открывается компактный выбор логов, а не выбирается случайная запись.
10. Пользователь может искать по номеру трубы, номеру bundle, названию списка и Log No.

## 3. Правила данных и статусов

### Нормализация

- Номер трубы сохраняется в каноническом виде: удаляются внешние пробелы и пробелы вокруг `/`; сравнение выполняется без учёта регистра.
- Допустимый первый формат: `<bundle>/<номер трубы>`, где обе части непустые. Неправильные строки не сохраняются; рядом с каждой строкой показывается ошибка.
- Bundle для планирования выводится из части слева от последнего `/`; номер трубы для сортировки -- из части справа.
- Bundle и номер трубы сортируются natural sort: сначала числовые значения, затем текстовые, поэтому `.../2` находится перед `.../12`.
- Одна и та же труба может быть в разных списках, но не может быть дважды в одном списке.

### Источник готовности

- Единственный источник зелёного статуса: точное совпадение `PlannedTestPipe.pipe_number` с `Pipe.pipe_number` из active `TestRevision.is_primary = true` со статусом `complete` или `confirmed` и `PressureTest.is_archived = false`.
- Черновик, архивный лог и не-primary revision не делают трубу зелёной.
- Зелёный статус вычисляется сервером при выдаче списка и не сохраняется отдельным флагом. Поэтому удаление, архивирование, восстановление и смена primary revision сразу отражаются корректно.
- Если совпадений несколько, API возвращает все подходящие логи, отсортированные по последнему обновлению. Интерфейс показывает число логов и предлагает выбрать нужный.
- Отсутствие номера трубы в логах не является ошибкой: это ожидающее состояние, серый цвет.

### Редактирование и удаление

- Владелец списка может переименовать список, изменить описание и добавить новые трубы.
- Для каждой серой строки доступны: редактировать номер и удалить.
- Зелёную строку нельзя менять случайно: перед редактированием выводится подтверждение, что связь с текущим логом может исчезнуть. Сам лог не меняется.
- Изменение номера проходит ту же нормализацию и проверку дубля; при совпадении с существующей строкой сохранение отклоняется с понятной ошибкой.
- Удаление одной трубы требует подтверждения и физически удаляет только плановую строку, а не реальный лог и не его файлы.
- Удаление bundle в интерфейсе удаляет все плановые строки этого bundle только после подтверждения с точным количеством труб.
- Удаление списка сначала является soft delete, с восстановлением из его собственной корзины. Постоянное удаление списка допускается только после отдельного подтверждения; реальные логи никогда не удаляются этим действием.
- Все create/edit/delete/restore действия по плану пишутся в существующий `AuditEvent`.

## 4. Интеграция с текущим кодом

| Область | Использование | Что не меняется |
| --- | --- | --- |
| `Pipe`, `Bundle`, `PressureTest`, `TestRevision` | Только чтение для вычисления готовности, поиска и перехода в лог | Существующая обработка CSV, ревизии и поиск логов |
| `PressureTestRecord` / PTR | Не участвует в первом этапе | Составные отчёты и их ссылки на логи |
| `App.tsx` | Новая вкладка рядом с Tests, PTR и FAQ | Existing Tests, Trash, Records и FAQ остаются независимыми |
| `TestDetailModal` | Открывается существующая карточка выбранного готового лога | Разметка, файлы и права лога |
| `AuditEvent` | Новые действия `planned_list_*` и `planned_pipe_*` | Существующие аудит-события |

Новый план не будет переиспользовать таблицу `Pipe` для ручных ожидающих труб: она описывает уже загруженные тестовые ревизии. Для плана требуются отдельные таблицы.

## 5. Предлагаемая модель данных

### `planned_test_lists`

| Поле | Назначение |
| --- | --- |
| `id` | UUID |
| `name` | Обязательное понятное имя списка |
| `description` | Необязательная заметка, проект или зона |
| `is_archived` | Логическое удаление списка |
| `created_by_user_id`, `created_by_name` | Автор |
| `created_at`, `updated_at` | Аудит времени |

### `planned_test_pipes`

| Поле | Назначение |
| --- | --- |
| `id` | UUID |
| `planned_test_list_id` | Владелец строки |
| `pipe_number` | Нормализованный полный номер, например `122355/1` |
| `bundle_number` | Вычисленный bundle для эффективной группировки и поиска |
| `pipe_sort_key` | Нормализованный ключ natural sort для части после `/` |
| `created_at`, `updated_at` | Аудит времени |

Ограничения PostgreSQL:

- unique (`planned_test_list_id`, `pipe_number`);
- индексы для `planned_test_list_id`, `pipe_number`, `bundle_number`;
- Alembic migration только добавляет новые таблицы и индексы, не меняет существующие логи.

## 6. API-контракт первой версии

Все операции находятся в новом изолированном роутере `/api/v1/planned-tests`.

| Метод | Маршрут | Назначение |
| --- | --- | --- |
| `GET` | `/lists?q=` | Списки, поиск по имени/описанию |
| `POST` | `/lists` | Создать список |
| `PATCH` | `/lists/{list_id}` | Переименовать или изменить описание |
| `DELETE` | `/lists/{list_id}` | Переместить список в корзину |
| `POST` | `/lists/{list_id}/restore` | Восстановить список |
| `DELETE` | `/lists/{list_id}/permanent` | Удалить только плановый список навсегда |
| `GET` | `/lists/{list_id}/pipes?q=&bundle=` | Группы, поиск и вычисленные статусы |
| `POST` | `/lists/{list_id}/pipes/bulk` | Добавить строки из multi-line input атомарно |
| `PATCH` | `/pipes/{pipe_id}` | Исправить номер трубы |
| `DELETE` | `/pipes/{pipe_id}` | Удалить одну плановую трубу |
| `DELETE` | `/lists/{list_id}/bundles/{bundle_number}` | Удалить все плановые строки bundle после подтверждения в UI |

Ответ списка труб содержит `status: pending | completed`, а для completed -- массив `matching_logs` с `log_no`, `pressure_test_id`, `revision_id`, датой и статусом. Это исключает отдельный клиентский расчёт и N+1 запросы.

Права первой версии:

- любой авторизованный пользователь: просмотр, поиск и открытие готового лога;
- `foreman` / `admin`: создание, импорт, редактирование, удаление, восстановление и permanent delete;
- решение о персональном владении списками можно добавить позже без миграции данных.

## 7. Интерфейс и локализация

### Навигация

- Вкладка: `План опрессовки` / `Pressure Test Plan` / `Painekoesuunnitelma`.
- Иконка: `ClipboardList` из Lucide.
- Счётчик в шапке списка: всего, готово, ожидает.

### Рабочая область

- Левая компактная колонка: списки и кнопка создания.
- Основная область: имя списка, быстрый поиск, фильтры `Все`, `Ожидают`, `Готово`, поле bundle.
- Группа bundle имеет заголовок, счётчик `готово / всего` и действия для добавления/удаления строк bundle.
- Строка трубы имеет стабильную ширину: цветовой статус, номер трубы, статус, Log No. при готовности, меню действий.
- Серый: нейтральная поверхность и метка `Ожидает`.
- Зелёный: `var(--accent-emerald)`, явный Log No. и курсор перехода.
- Цвет не единственный сигнал: используются текст статуса и иконка `CheckCircle2` / `Clock3`.
- Поиск не скрывает bundle: совпавшая строка остаётся внутри своей группы, а заголовок показывает, почему группа видна.
- Новые строки, ошибки, подтверждения, empty states и tooltips добавляются в `i18n.ts` для EN/FI/RU.
- Закрытие всех новых modal-окон: только крестик и `Esc`; клик по фону не закрывает форму.

## 9. Приёмочные критерии

- [ ] Можно создать несколько планов опрессовки.
- [ ] Multi-line input корректно добавляет `122355/1` и `123561/12`.
- [ ] Неверные строки и дубли не сохраняются и показывают номер проблемной строки.
- [ ] Трубы сгруппированы по bundle; номера в группе сортируются `1`, `2`, `12`.
- [ ] Поиск находит строку по полному номеру трубы, bundle, имени списка и Log No.
- [ ] Труба без точного активного primary log серая и имеет текстовый статус ожидания.
- [ ] Труба с точным активным primary log зелёная, отображает Log No. и открывает его карточку.
- [ ] Архивный лог и draft не отмечают трубу готовой.
- [ ] Опечатку можно исправить; дубликат в том же списке не создаётся.
- [ ] Удаление трубы/bundle/списка никогда не удаляет Pressure Test, CSV, artifact или PTR.
- [ ] Все новые тексты есть на EN/FI/RU; новые модальные окна закрываются крестиком и `Esc`.
- [ ] Все изменения плана аудитируются.

## 10. Открытые решения перед реализацией

1. Нужны ли планам дополнительные обязательные поля: проект, система, дата/неделя, ответственный, drawing/spool?
2. Может ли оператор редактировать только созданный им список, или управление остаётся у foreman/admin?
3. Нужно ли выгружать план в Excel/PDF в первой версии или это отдельный этап?
4. Считать ли трубу зелёной при наличии `complete` или `confirmed` active log, либо только `confirmed` log? В этом roadmap предложено: active primary revision с состоянием `complete` или `confirmed`; draft не учитывается.
5. Нужно ли ручное исключение/причина для трубы, которая больше не требует опрессовки? Не добавлять без явного решения, чтобы серый статус не скрывал фактическую незавершённость.

## 11. Что намеренно не входит в первую версию

- создание тестового лога или CSV прямо из плана;
- автоматическое изменение PipeCloud;
- изменение или генерация PTR;
- массовая загрузка Excel;
- назначение людей, сроков, уведомления и календарь;
- изменение существующих `Pipe`, `Bundle`, `PressureTest` и history revisions.

Эти функции можно добавить после того, как базовый список и автоматическая сверка с логами пройдут приёмку.
