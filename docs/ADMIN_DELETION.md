# Удаление фото и архивного лога администратором

Обычное удаление лога по-прежнему перемещает его в корзину. Foreman может
архивировать и восстанавливать лог. Физическое удаление доступно только Admin,
после подтверждения в интерфейсе. Автоматической очистки нет.

## Контракт API

- `DELETE /api/v1/tests/artifacts/{artifact_id}` удаляет только фото (`file_type=photo`)
  из активного лога и возвращает обновлённый `PressureTestResponse`.
- `DELETE /api/v1/tests/{log_no}/permanent?test_id={id}` удаляет выбранный архивный
  лог, все его ревизии, трубы, наборы, вложения и публичные share-записи.
  Возвращает `200` с JSON `null`, как и прежний маршрут.
- `test_id` — стабильный ID выбранной карточки в корзине. Старый вызов без ID
  допускается только при единственном архивном логе с таким номером.
  Несколько совпадений дают `409`, несовпадение ID/номера или активный лог — `404`.
- Неаутентифицированный запрос получает `401`, Foreman/Viewer — `403`.
  Для браузерной сессии действуют обычные Origin/CSRF-проверки.
- Удаление отдельного CSV, графика или отчёта даёт `400`.
- Ссылка из PTR на лог или файл блокирует окончательное удаление (`409`).
  Проверяются также архивные PTR, исключённые из PDF вложения и старые ссылки
  на файл только по `storage_key`, без `artifact_id`.
- Файл, используемый другим вложением, также защищён (`409`).

Audit-события `photo_deleted` и `test_permanently_deleted` сохраняют автора,
время, ID, номер лога и сведения об удалении. Старый аудит остаётся в базе.
Удаление и новое audit-событие фиксируются одной транзакцией. Изменений схемы
и миграций нет; формат desktop-ревизий и локальных папок прежний.

## Ошибки и восстановление

Перед SQL DELETE файлы перемещаются внутри того же хранилища в `.deletions/`.
Для каждого файла заранее записывается JSON-квитанция с `original_key` и
`staged_key`. При обычной ошибке перемещения или транзакции файлы возвращаются
на исходные места, SQL-изменения откатываются. Отсутствующий исходный файл
не мешает удалить оставшуюся запись. Каталоги, выход за корень хранилища и
символические ссылки удалить таким способом нельзя.

После commit временные файлы и квитанции уничтожаются. Если очистка диска
не удалась, API сообщает `500` с явным пояснением, что объект уже удалён:
нужно обновить список. Остатки остаются в `.deletions/`; их ключи сохранены
в `AuditEvent.details_json.files`. Очистка остальных файлов продолжается.

Если процесс прерван, ручное восстановление выполняется при остановленных
запросах записи, на копии базы и хранилища перед применением к рабочим данным:

1. Прочитать квитанции `.deletions/*.json`.
2. Для каждой квитанции найти commit удаления по соответствующему `staged_key`
   в `photo_deleted`/`test_permanently_deleted` audit-событиях.
3. Если commit есть, завершить очистку через `storage.finalize_file_deletion()`.
4. Если commit нет и исходная запись вложения существует, вернуть файл через
   `storage.restore_file_deletion()`. Метод не перезаписывает новый файл.
5. Если состояние неоднозначно, сохранить квитанцию и файл для разбора.

Не удалять `.deletions/` целиком: там могут лежать файлы незавершённой транзакции.
Автоматическая очистка при старте не вводится. Перемещение файлов и commit БД
не являются общей распределённой транзакцией; квитанции нужны для восстановления
после остановки процесса между этими шагами.

## Ручной сценарий на синтетических данных

1. Войти как Admin, открыть активный лог с фото и графиком.
2. В списке файлов удалить фото, подтвердить действие: фото исчезает из карточки,
   список обновляется, скачивание удалённого ID возвращает `404`. У графика и CSV
   нет кнопки физического удаления.
3. Обычной кнопкой удалить лог, открыть его в корзине, выбрать «Удалить навсегда».
   После подтверждения карточка исчезает; файлы и share-записи удалены, аудит сохранён.
4. Повторить для фото/PTR и лога/PTR: получить отказ без потери файлов.
5. Войти как Foreman или Viewer: кнопки физического удаления отсутствуют,
   прямые запросы к этим маршрутам получают `403`.

Автоматические проверки: `test_restore_and_permanent_delete_safety.py`,
`test_storage_deletion.py`, `test_trash_read_only.py`, `test_mobile_ux_audit_fixes.py`.
Использовать изолированные `ARDOR_ENV=test`, SQLite `DATABASE_URL` и временный
`STORAGE_DIR`, затем выполнить `python -m pytest` с этими файлами.
