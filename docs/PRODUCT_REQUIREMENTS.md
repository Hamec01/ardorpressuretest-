# ARDOR Pressure Test — требования продукта

**Статус:** Approved 1.0  
**Дата:** 2026-08-19  
**Цель документа:** зафиксировать утверждённые решения заказчика для развития системы.

## 1. Видение

ARDOR Pressure Test — внутренняя система для обработки гидравлических и пневматических испытаний, хранения доказательных материалов, быстрого поиска и выпуска производственных документов.

Продукт состоит из двух связанных рабочих областей:

1. **Pressure Analysis** — рабочее место оператора: CSV WIKA → анализ → график → XLSX/TXT/PDF → фотографии → ревизия лога.
2. **Pressure Test Records** — рабочее место прораба/начальства: выбор одного или нескольких логов, дополнение производственных данных и формирование официального ARDOR Pressure Test Record.

## 2. Стратегия запуска

1. Сначала всё разворачивается локально.
2. Существующее Windows-приложение сохраняет офлайн-работу.
3. Локальный сервер, PostgreSQL, файловое хранилище и веб-интерфейс проверяются на одном компьютере.
4. После полного локального приёмочного теста система переносится в отдельное staging-окружение Ubuntu/Docker.
5. Production возможен только после демонстрации и отдельного решения начальства.

## 3. Пользователи

- работники/операторы;
- прорабы;
- начальство;
- администраторы.

Должность и системные разрешения хранятся раздельно. В обычной работе сотрудники имеют схожие права на доступные материалы. Администратор создаёт аккаунты и назначает должности/разрешения. Прораб может управлять участниками в доступном контексте.

## 4. Доступ

1. По умолчанию новые проекты видны всем сотрудникам.
2. Администратор может скрыть отдельное направление, проект или набор данных от выбранного сотрудника.
3. Система должна поддержать будущие направления, например FE и ISIS.
4. Любой сотрудник с доступом может искать, просматривать и скачивать файлы.
5. Право подтверждения назначается отдельно аккаунту; обычно оно есть у прорабов, начальства и администратора.

## 5. Основные понятия

- **Log** — уникальная карточка испытания с единственным `Log No.` во всей системе.
- **Revision** — неизменяемый комплект файлов и метаданных одного создания/изменения лога.
- **Artifact** — CSV, PNG, XLSX, TXT, PDF, фотография или дополнительный документ.
- **Project** — необязательная группировка. Точное бизнес-значение пока не утверждено.
- **Pressure Test Record** — официальный документ, объединяющий производственные строки и один или несколько логов.
- **Primary revision** — выбранная прорабом или администратором основная версия лога.

## 6. Создание испытания

### 6.1 Правило первой версии

Один исходный CSV соответствует одному `Log No.` и одной новой ревизии.

### 6.2 Обязательные данные для Complete

- уникальный Log No.;
- дата испытания;
- требуемое давление, bar;
- минимум один номер трубы;
- минимум один номер бандла;
- оператор/автор;
- минимум одна фотография труб;
- минимум одна фотография манометра;
- успешно прочитанный исходный CSV;
- сформированные обязательные отчёты.

Неполное испытание можно сохранить как Draft.

### 6.3 Ввод труб и бандлов

- ручной ввод отдельными значениями;
- вставка списка строками или через запятую;
- автоматическое удаление пустых значений и точных повторов;
- сохранение исходного производственного написания;
- отображение предупреждения при подозрительных дубликатах.

## 7. Файлы ревизии

Одна полноценная ревизия может содержать:

- исходный CSV;
- PNG-график;
- XLSX;
- TXT;
- PDF-рапорт;
- фотографии труб;
- фотографии манометра;
- фотографии установки/объекта;
- прочие фотографии;
- дополнительные документы;
- manifest с контрольными суммами и версиями генераторов.

Файлы можно просмотреть, скачать отдельно, выбрать несколько или скачать всю ревизию ZIP-архивом.

## 8. Состояния

### 8.1 Лог/ревизия

- `Draft` — обязательные материалы ещё не собраны.
- `Processing` — идёт создание отчётов.
- `Review` — программа или сотрудник обнаружили неоднозначность.
- `Complete` — обязательный комплект сформирован.
- `Confirmed` — выбранная ревизия подтверждена уполномоченным аккаунтом.
- `Archived` — скрыта из обычной работы, но хранится.
- `Deleted` — логически удалена, доступна для аудита и восстановления.

### 8.2 Подтверждение

- подтверждение необязательно;
- подтверждённая ревизия блокируется;
- создаётся отдельный confirmed PDF;
- PDF содержит уникальный номер документа, имя, должность, дату и время;
- последующее изменение создаёт новую неподтверждённую ревизию.

## 9. Параллельное редактирование

1. Два сотрудника могут редактировать один лог.
2. Каждый результат создаёт отдельную ревизию.
3. Ничего не перезаписывается автоматически.
4. Прораб или администратор назначает основную ревизию.
5. История показывает автора, дату, время, основание и изменения.

## 10. Предварительная оценка PASS/FAIL

Утверждённое направление, требующее проверки на реальных CSV:

1. Оператор вводит одно общее минимальное требуемое давление.
2. Оценивается последний полный час пригодной записи.
3. Намеренный сброс давления не входит в CSV.
4. Если давление на зачётном участке опускается ниже требуемого, программа предлагает `Failed`.
5. Если пригодных данных меньше одного часа, программа предлагает `Failed`.
6. Человек может изменить предложенный результат с обязательной причиной.
7. Автоматическая оценка и окончательное решение хранятся раздельно.

**Открыто:** допустимое кратковременное отклонение и правило `0,5 bar` не утверждены.

## 11. Поиск

Единая строка ищет по:

- Log No.;
- Pipe No.;
- Bundle No.;
- дате;
- требуемому давлению;
- Min/Max;
- Job No.;
- Sales Order No.;
- Project;
- Inspection Number;
- Drawing No.;
- System;
- Part No.;
- Ship/Vessel;
- Customer;
- WIKA/Meter No.;
- оператору;
- примечанию;
- имени файла.

Приоритет: точный Log No. → точный Pipe No. → точный Bundle No. → текущий контекст → новые совпадения.

## 12. Desktop и синхронизация

1. Windows-приложение полностью работает офлайн.
2. Логи добавляются в видимую очередь.
3. Пользователь выбирает момент синхронизации.
4. Передаётся полный комплект ревизии, история и переносимые настройки.
5. Повторная отправка безопасна и не создаёт дубликаты.
6. Существующий Log No. создаёт новую ревизию.
7. Обновления Windows-приложения публикуются через GitHub Releases.
8. Пользователь получает уведомление и подтверждает установку.

## 13. Pressure Test Record

### 13.1 Первая версия

Один точный шаблон ARDOR на основе предоставленного образца.

### 13.2 Поля шапки

- page/pages totally;
- Inspection Number;
- Job No.;
- Sales Order No.;
- Project No. or Name;
- Ship/Vessel Name;
- Customer;
- Design Pressure;
- Test Pressure;
- Meter/WIKA Number.

### 13.3 Строки

- Drawing No.;
- System;
- Part No.;
- Date;
- Duration of Test;
- Log No.

Один документ может содержать несколько логов. Один лог может использоваться в нескольких строках.

### 13.4 Прочие поля

- Test Material: Air, Water, Glycol, Nitrogen;
- Reviewed;
- Approved;
- Remarks;
- дата;
- имя/должность проверяющего.

### 13.5 Процесс

- прораб создаёт пустой черновик или начинает из готового лога;
- добавляет/удаляет логи через поиск;
- автоматически подтянутые значения отмечаются;
- ручные поля доступны для дополнения;
- PDF формируется только после валидации;
- способы подписи вариативны: печать, изображение, подтверждение аккаунтом, загрузка подписанного PDF;
- эти способы хранятся как отдельные состояния.

## 14. Интерфейс

- продукт: `ARDOR Pressure Test`;
- языки: English, Suomi, Русский;
- язык сохраняется в профиле;
- основные устройства: Windows PC, планшеты, домашние компьютеры руководства;
- первый экран после входа ориентирован на поиск и создание испытания;
- интерфейс быстрый, светлый, без перегруженного dashboard.

## 15. Уведомления

- лог обработан;
- ошибка обработки;
- ошибка синхронизации;
- другой сотрудник изменил лог;
- отчёт подтверждён;
- доступно обновление приложения;
- доступ к проекту открыт/закрыт.

## 16. Хранение и удаление

- старые ревизии хранятся постоянно;
- удалённые материалы не уничтожаются через обычный UI;
- любое удаление записывается в аудит;
- данные могут быть восстановлены;
- политика окончательной очистки не входит в первую версию.

## 17. Восстановление аккаунта

- ссылка по email;
- администратор выдаёт временный пароль;
- временный пароль обязательно меняется при входе.

## 18. Не входит в первый релиз

- визуальный редактор шаблонов;
- пакетная обработка нескольких CSV;
- несколько шаблонов заказчиков;
- сертифицированная электронная подпись;
- автоматическое признание результата без участия человека;
- production-развёртывание;
- сложная аналитика и BI;
- нативное мобильное приложение.

## 19. Открытые решения

1. Точное значение сущности Project.
2. Инженерный допуск колебаний/падения.
3. Достаточно ли одной точки ниже порога для FAIL или нужна фильтрация датчика.
4. Окончательный набор обязательных полей Pressure Test Record.
5. Правила нумерации confirmed PDF.
6. Способ внешнего доступа: internet, internal network или VPN.
7. Регламент резервного хранения компании.
