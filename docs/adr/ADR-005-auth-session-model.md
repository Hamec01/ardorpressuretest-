## 1. Контекст (доказательная база)

R0-A (статический анализ на указанном HEAD) подтвердил 17 находок F01–F17: fail-open `require_role` (`services/api/auth.py:152-160,166-168,181-184`), 21 из 45 маршрутов без auth dependency, отсутствие AuthGate в `apps/web/src/App.tsx`, общий приватный/публичный API-контракт для share (`apps/web/src/components/PublicLogView.tsx:18`), отсутствие владельца у `PressureTest`/`TestRevision`/`PressureTestRecord`, in-place редактирование ревизий и PTR (`services/api/routes/tests.py:437-538`, `services/api/routes/records.py:711-744`), деструктивный `GET /tests/trash` (`services/api/routes/tests.py:162-172,234-236`), отсутствие containment/SHA-проверки в storage/sync (`services/api/storage.py:27-28`, `services/api/routes/sync.py:60-75`).

Runtime baseline подтверждён отдельно: то же дерево развёрнуто как публично доступный staging (`http://84.247.130.242:8080/`, на момент принятия — HTTP без TLS; контейнеры `ardor_web_staging`/`ardor_api_staging`/`ardor_postgres_staging`, compose-проект `deploy`, сеть `deploy_default`). Экстренная сетевая mitigation через IP-allowlist была рассмотрена и отклонена (динамический IP владельца). Application-level авторизация (§8/§9) и HTTPS обязательны и не заменяются сетевым уровнем; Let's Encrypt IP-сертификат утверждён как способ получить HTTPS без домена (см. §15). WireGuard пока не утверждён к внедрению — это необязательный будущий defense-in-depth слой, требующий отдельного решения владельца, не часть текущего плана.

Этот раздел фиксирует факты кода на момент принятия — все решения ниже.

## 2. Роли аккаунтов — ровно три

| Роль | Назначение |
|---|---|
| `admin` | Полный доступ, включая управление аккаунтами и справочником манометров |
| `foreman` | Все рабочие операции со всеми логами, планами, PTR, sync, файлами и share; без доступа к управлению аккаунтами |
| `viewer` | Просмотр и скачивание всех внутренних материалов; без мутаций, без создания share |

`operator`/`manager` — не целевые роли. Значение `role` в текущей БД (`services/api/models.py:24`, default `"operator"`) не переименовывается автоматически ни в одну из трёх новых: каждый существующий `operator`/`manager`-аккаунт сопоставляется вручную владельцем на этапе R2.

`foreman_matti` — отдельное исключение, не часть этого ручного сопоставления. Это seed-аккаунт (`services/api/auth.py:110`), а не реальный сотрудник; его роль отдельно не выбирается — материалы, приписанные `foreman_matti`, переназначаются реальному аккаунту Andrei Sakki с ролью `admin` по правилам §13.

Персональная permission matrix (поля `log_access`, `can_create_reports`, `pressure_test_plan_access`, `can_manage_shares`) **отменена** — права определяются ролью целиком, без per-объектного override.

## 3. Capability matrix

`Public guest` — не значение `User.role`, а отсутствие сессии. Единственная возможность гостя — открыть то, что Admin/Foreman явно опубликовали через share.

| Возможность | Admin | Foreman | Viewer | Public guest |
|---|---|---|---|---|
| Аккаунты (создание/роль/пароль/деактивация) | Да | Нет | Нет | Нет |
| Список аккаунтов (чтение) | Да | Нет | Нет | Нет |
| Логи (просмотр/поиск/история) | Да | Да | Да (чтение) | Нет |
| Metadata (редактирование) | Да, с integrity-ограничениями | Да, с integrity-ограничениями | Нет | Нет |
| Downloads (файл/ZIP/PDF) | Да | Да | Да | Только опубликованные вложения через share |
| Archive/restore | Да | Да | Нет | Нет |
| Physical delete | **Нет — запрещено системно** | Нет | Нет | Нет |
| Планы опрессовки | Читает и изменяет | Читает и изменяет | Читает и скачивает | Нет |
| PTR | Создаёт/редактирует | Создаёт/редактирует | Читает и скачивает | Нет |
| Confirm/sign PTR | Да, только от своего имени | Да, только от своего имени | Нет | Нет |
| Sync (Windows-клиент) | Да | Да | Нет | Нет |
| Share (создание/отзыв) | Да | Да | Нет | N/A — потребитель |
| Справочник манометров | Добавляет/редактирует/деактивирует | Выбирает активный | Видит выбранный | Нет |

## 4. Integrity constraints — действуют вне зависимости от роли

- Physical delete запрещён всем без исключения, включая Admin — системный запрет, не отсутствие прав.
- Confirmed/Complete-материал не редактируется in-place: любое изменение создаёт новую ревизию/запись.
- Confirm/sign PTR фиксирует `confirmed_by_*` строго из сессии актёра, не из payload, ни для кого.

## 5. Draft/Complete

Создают/редактируют Admin и Foreman; Viewer — только чтение. Draft — с пустыми метаданными. Complete требует Log No. и активный манометр из справочника. **Test Pressure необязателен даже для Complete**; без него результат — `Не оценён`, без PASS/FAIL. Это формально пересматривает `docs/PRODUCT_REQUIREMENTS.md §6.2/§10` в редакции 1.0 — документ синхронизирован отдельно (см. также ревизию 1.1). Остальные поля необязательны, без искусственных defaults. Изменение Complete/Confirmed — только новой ревизией.

## 6. Справочник манометров и Gauge history

### 6.1 Базовая модель

Новая сущность, в коде на момент принятия отсутствует (`wika_nr` — свободный текст, `services/api/routes/process.py:149`, `services/api/routes/tests.py` `TestMetadataUpdate.wika_nr`). Admin добавляет/редактирует/деактивирует записи; Foreman выбирает активный манометр при создании/редактировании теста (не вводит текст); Viewer видит выбранное, без права менять. Draft — без манометра; Complete требует активный. `WIKA Gauge Serial` — выбор из справочника (FK), не текст с default.

### 6.2 Gauge history — почему одного mutable FK недостаточно

Одной ссылки `gauge_id` мало: если запись справочника отредактирована (изменён серийный номер/модель) или деактивирована, при наивной реализации через чистый FK старое испытание задним числом «переехало» бы на новые данные манометра — та же проблема неизменяемости, что и F14.

Зафиксировано:
- `Gauge` имеет стабильный ID.
- `TestRevision` хранит **и** `gauge_id` (для фильтрации/отчётности/администрирования), **и** immutable snapshot — минимум серийного номера — записанный в саму ревизию/manifest в момент фиксации, а не читаемый на лету из справочника.
- При необходимости snapshot дополнительно включает модель и калибровочные данные — состав уточняется на R2, серийный номер обязателен.
- Редактирование или деактивация записи справочника влияет только на будущий выбор для новых Draft/Complete.
- Историческая ревизия всегда показывает исходный snapshot серийного номера независимо от текущего состояния справочника.

## 8. Browser session lifecycle

- Сессия — Secure + HttpOnly + SameSite cookie, работает только по HTTPS. Жёсткая зависимость от §15: пока на публичном адресе нет HTTPS, эта модель не может быть включена в live (браузер не отправит Secure-cookie по HTTP).
- CSRF-защита всех мутирующих запросов с cookie-auth.
- Session/access/refresh token не хранится в `localStorage` и не передаётся в URL — заменяет текущий `localStorage.getItem('ardor_token')` (`apps/web/src/context/AuthContext.tsx:23`).
- Logout отзывает текущую сессию на сервере (не просто `localStorage.removeItem`, как сейчас в `AuthContext.tsx:79-83`).
- Смена/сброс пароля и деактивация аккаунта отзывают все сессии аккаунта, не только текущую.
- Роль, активность и права проверяются сервером на каждом запросе — без окна устаревших прав и без fallback-путей (закрывает F01 полностью).
- Последнего активного Admin нельзя деактивировать или понизить в роли, включая конкурентные запросы.
- Старый `ardor_token` очищается на клиенте при переходе на новую схему.

## 9. Desktop session lifecycle

- Отдельный bearer/device flow, не browser cookie.
- Секрет устройства хранится в Windows credential storage.
- Секрет не хранится в `config.json`, manifest или SQLite-очереди (`src/wika_report/sync_queue.py:50-64` сегодня и так не содержит такого поля — состояние сохраняется).
- Локальная обработка CSV работает полностью без интернета — не меняется этой моделью.
- Авторизация требуется только на этапе обмена с сервером (`services/api/routes/sync.py` — sessions/upload/complete).
- 401 останавливает отправку и требует повторный вход, сохраняя локальные файлы и очередь. 403 показывает причину отказа. Ни 401, ни 403 не удаляют локальные данные и не помечают элемент очереди как `synced` (уточняет сегодняшнюю обработку ошибок в `src/wika_report/sync_client.py:125-129`).

## 10. Private/public API boundary

- Все business API закрыты по умолчанию.
- Публичны только: `login`, согласованный `health`, и отдельные public-share endpoints (новый `services/api/routes/shares.py`, R5).
- **Docs/OpenAPI policy:** в любом публично достижимом окружении `/docs`, `/redoc`, `/openapi.json` закрываются (отключаются или требуют авторизации) — на момент принятия `services/api/main.py` не задаёт `docs_url=None`/`openapi_url=None`, они включены по умолчанию. В изолированной локальной разработке могут оставаться открытыми.
- Share-токен — криптографически случайный; в БД хранится только hash, не сам токен.
- Публичный DTO не является внутренним `PressureTestResponse`/PTR/Plan-ответом — отдельная public-схема с явным списком полей.
- Каждый запрос файла/PDF/ZIP проверяется через конкретную публикацию: токен, срок/отзыв, и принадлежность запрошенного файла именно этой публикации.
- Гость не может подставить чужой artifact/resource ID — сервер проверяет членство ID в опубликованном наборе.
- Старый `/share/{log_no}` отключается без автоматической миграции.
- Публичное чтение не создаёт внутреннюю сессию и не допускает мутаций.

## 11. Ownership and audit

- `created_by_user_id`/`updated_by_user_id` берутся только из серверной сессии, никогда из клиентского payload — распространяет существующий паттерн `PlannedTestList.created_by_user_id` (`services/api/routes/planned_tests.py:236`) на `PressureTest`/`TestRevision`/`PressureTestRecord`, где владельца сегодня нет вовсе (F07).
- Редактор чужого объекта не становится его владельцем: `updated_by_user_id` меняется, `created_by_user_id` — нет.
- Строковые `operator` (`TestRevision.operator`, `models.py:65`) и `foreman_name` (`PressureTestRecord.foreman_name`, `models.py:173`) остаются полями отображения, не используются как доказательство владения.
- Изменения аккаунтов, ролей, share и подтверждений пишутся атомарно с бизнес-транзакцией — отдельный `db.commit()` внутри `log_audit_event` (`services/api/audit.py:32-34`, F12) для этих категорий должен быть исключён или объединён с бизнес-изменением в одну транзакцию с откатом при сбое любой из частей.
- Пароли, хеши, cookies и полные share-токены не журналируются.
- Legacy-переназначение на Andrei Sakki сохраняет прежнюю атрибуцию в audit (§13) — не затирает исходное значение.

## 15. HTTPS without a domain

Владелец одобрил бесплатный сертификат Let's Encrypt непосредственно для IP-адреса (без домена) с автоматическим продлением.

- Let's Encrypt поддерживает выпуск сертификатов напрямую на IPv4/IPv6-адреса. Источник: [letsencrypt.org/2026/01/15/6day-and-ip-general-availability](https://letsencrypt.org/2026/01/15/6day-and-ip-general-availability).
- Используется short-lived certificate — срок действия порядка 160 часов. Источник: [letsencrypt.org/2026/03/11/shorter-certs-certbot](https://letsencrypt.org/2026/03/11/shorter-certs-certbot).
- При таком коротком сроке действия обязательно полностью автоматическое ACME-продление — ручное обновление не является жизнеспособным процессом. Соответствующие профили описаны в [letsencrypt.org/docs/profiles](https://letsencrypt.org/docs/profiles/).
- Отказ автопродления должен обнаруживаться мониторингом (алерт задолго до истечения короткого срока действия), а не постфактум по жалобам пользователей.
- **Сертификат не запрашивается и не устанавливается в рамках R0.** Это решение фиксирует одобрение подхода, не его исполнение.
- Изменение nginx-конфигурации и открытых портов выполняется только отдельным infra-этапом, вне документационного R0-C.
- Secure-cookie (§8) не включается в live до того, как HTTPS на публичном адресе фактически проверен и подтверждён работающим.
- Прямой внешний доступ к API-порту `:8000` впоследствии закрывается полностью (согласуется с ранее рассмотренной, но не применённой сетевой mitigation) — это отдельное действие после появления HTTPS, не часть выпуска сертификата.
- WireGuard пока **не утверждён к внедрению**. Application-level авторизация (§8/§9) и HTTPS обязательны сами по себе и не зависят от WireGuard. Если WireGuard будет утверждён отдельным решением владельца, он останется необязательным дополнительным defense-in-depth слоем сетевого уровня, а не заменой application-level авторизации.

## 17. R0 Runtime Inventory — подтверждено read-only (2026-09-15)
