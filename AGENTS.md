## 1. Назначение документа

Этот файл определяет обязательные правила для любого AI-агента или разработчика, который анализирует, проектирует или изменяет ARDOR Pressure Test. Цель правил — сохранить работающее локальное приложение, не потерять производственные материалы и развивать систему по утверждённым этапам.

Если задача противоречит этому документу, агент обязан остановиться, описать конфликт и запросить решение заказчика. Нельзя молча выбирать более широкий объём работ.

## 2. Текущий режим проекта

1. Проект находится на стадии предпроектирования и локальной разработки.
2. Существующее Windows-приложение является рабочей базой и не должно ломаться ради будущего сайта.
3. До отдельного письменного разрешения запрещено:
   - развёртывать production;
   - изменять работающие проекты на Ubuntu-сервере;
   - подключаться к production PostgreSQL;
   - публиковать реальные производственные файлы;
   - выполнять необратимые миграции;
   - удалять старые логи и ревизии;
   - переписывать всё приложение с нуля.
4. Разработка идёт в последовательности: локальная среда → автоматические проверки → локальный приёмочный сценарий → отдельное staging-окружение Ubuntu → демонстрация начальству → отдельное решение о production.

## 3. Источники истины

Приоритет требований:

1. Явное последнее решение заказчика.
2. Утверждённый `PRODUCT_REQUIREMENTS.md`.
3. Утверждённая техническая архитектура.
4. Утверждённый roadmap и текущий этап.
5. Фактическое поведение проверенного кода.
6. README и старые комментарии в коде.

README или текущая реализация не отменяют более новое утверждённое бизнес-решение. Если код и документация расходятся, агент фиксирует расхождение, но не исправляет его за пределами поставленной задачи.

## 4. Обязательный порядок начала каждой задачи

Перед изменениями агент обязан:

1. Прочитать `AGENTS.md`, требования, архитектуру, roadmap и относящиеся к задаче ADR.
2. Проверить репозиторий, ветку, HEAD и рабочее дерево.
3. Сообщить, если рабочее дерево уже содержит чужие изменения.
4. Зафиксировать точный объём задачи и критерии готовности.
5. Найти реальные кодовые пути, связанные с задачей.
6. Назвать предполагаемые файлы изменений.
7. Не начинать следующий этап roadmap без отдельного разрешения.

## 5. Работа с Git

1. Не работать напрямую в `main`, если задача включает изменения.
2. Для каждого утверждённого этапа использовать отдельную ветку.
3. Не делать commit, push, merge, tag или release без явного разрешения в задаче.
4. Не использовать `git reset --hard`, принудительный push и переписывание истории без отдельного согласования и резервной копии.
5. Не добавлять в Git:
   - реальные CSV заказчиков;
   - фотографии труб и манометров;
   - готовые PDF/XLSX с производственными данными;
   - пароли, токены, `.env`;
   - локальные базы данных;
   - runtime-папки;
   - собранные `.exe` и большие ZIP-релизы.
6. Готовые Windows-сборки публикуются через GitHub Releases после появления утверждённого release-процесса.
7. Commit должен быть небольшим, тематическим и проверяемым. Нельзя смешивать рефакторинг, новую функцию и случайное форматирование.

## 6. Безопасность производственных данных

1. Исходный CSV является неизменяемым доказательным материалом.
2. После приёма рассчитывается SHA-256 каждого файла.
3. Результаты одной обработки сохраняются как атомарная ревизия с манифестом.
4. Повторная обработка не перезаписывает предыдущую ревизию.
5. Удаление в пользовательском интерфейсе является логическим; данные и журнал сохраняются.
6. Подтверждённая ревизия неизменяема. Исправление создаёт новую ревизию.
7. Любое изменение бизнес-данных фиксирует автора, время, причину и ссылку на предыдущую версию.
8. Тесты используют синтетические или обезличенные материалы.
9. Логи приложения не должны содержать пароли, токены, полные cookies и содержимое конфиденциальных документов.

## 7. Архитектурные границы

1. Ядро обработки давления не зависит от Tkinter, FastAPI, React, PostgreSQL или конкретного хранилища.
2. Desktop GUI вызывает application/service layer, а не внутренние генераторы напрямую.
3. Web API использует то же ядро обработки, что и локальное приложение.
4. Метаданные хранятся в PostgreSQL; крупные файлы — через интерфейс файлового хранилища.
5. Локально используется filesystem backend. Возможный S3/MinIO backend добавляется позднее без изменения доменной модели.
6. Синхронизация работает через версионированный API и идемпотентные операции.
7. Нельзя связывать код домена с абсолютными Windows-путями.
8. Нельзя использовать имя файла как единственный идентификатор сущности.
9. `Log No.` хранится в нормализованном виде без автоматически добавленного `Log_`.
10. Один CSV соответствует одному `Log No.` и одной ревизии в первой версии.

## 8. Бизнес-правила нельзя придумывать

Агент не имеет права самостоятельно объявлять инженерные нормы. В частности:

- допустимое падение `0,5 bar` пока не утверждено;
- критерий PASS/FAIL является предварительной оценкой программы;
- окончательное решение может быть принято человеком;
- неясные нормы отмечаются как Open Decision;
- для нормативных утверждений требуется конкретный стандарт или утверждённый регламент компании.

Подтверждённое рабочее правило первой версии: оценивается последний полный час записи; давление не должно опускаться ниже введённого оператором требуемого значения; запись короче одного часа предлагается как FAIL. До реализации это правило должно получить отдельное подтверждение на реальных CSV.

## 9. API и синхронизация

1. Desktop продолжает работать без интернета.
2. Синхронизация запускается пользователем из видимой очереди.
3. Статусы очереди: `pending`, `uploading`, `synced`, `conflict`, `failed`.
4. Повтор запроса после сбоя не создаёт дубликат.
5. Сервер подтверждает приём только после проверки манифеста, размеров и SHA-256.
6. Новый `Log No.` создаёт лог; существующий — новую ревизию.
7. Конфликт не перезаписывает данные. Создаются отдельные ревизии, а основную выбирает прораб или администратор.
8. Клиент не считает файлы синхронизированными до получения устойчивого server receipt.
9. Настройки делятся на переносимые и локальные. Windows-пути и состояние окна не синхронизируются.
10. API меняется совместимо или получает новую версию `/api/v2`.

## 10. Pressure Test Record

1. Это отдельная сущность прораба, а не вариант графика.
2. Документ может включать несколько логов и несколько строк на один лог.
3. Первая версия поддерживает один точный шаблон ARDOR.
4. Inspection Number вводится вручную.
5. Документ можно начать до или после создания логов.
6. PDF без подписи, подтверждение аккаунтом, изображение подписи и загруженная подписанная копия — разные состояния/артефакты.
7. Подтверждённый PDF получает уникальный номер, имя, должность, дату и время подтверждения.
8. Исходный шаблон нельзя менять без visual regression проверки PDF.

## 11. Качество кода

Обязательно:

- type hints для нового Python-кода;
- TypeScript strict mode;
- форматирование и lint;
- unit-тесты доменной логики;
- integration-тесты базы, API и хранилища;
- end-to-end тест ключевого пользовательского потока;
- миграция Alembic для каждого изменения схемы;
- документация публичных API и форматов manifest;
- понятные ошибки для пользователя;
- корректная обработка Unicode, финского, русского и английского языков;
- временные файлы создаются в безопасном temp-каталоге и очищаются.

Запрещено считать задачу готовой только потому, что код компилируется.

## 12. Обязательная проверка перед завершением задачи

Агент должен сообщить:

1. Что именно изменено.
2. Что намеренно не изменялось.
3. Какие команды проверки запущены.
4. Какие тесты прошли или почему не были запущены.
5. Какие миграции добавлены.
6. Есть ли обратная совместимость со старой локальной папкой.
7. Есть ли новые риски или открытые решения.
8. Как вручную проверить пользовательский сценарий.
9. Точный git diff/status.

## 13. Stop conditions

Агент обязан остановиться и запросить решение, если:

- найден секрет или персональные данные в Git;
- требуется изменить production;
- задача требует удаления или перезаписи реальных материалов;
- неясно, какой `Log No.` или проект является целевым;
- миграция может потерять данные;
- реальное поведение расходится с утверждённым бизнес-правилом;
- требуется расширить scope на следующий этап;
- отсутствует необходимый реальный пример документа/CSV;
- нельзя доказать целостность ревизии.

## 14. Definition of Done

Функция готова только когда:

- выполнены её критерии приёмки;
- есть автоматические тесты;
- выполнен ручной рабочий сценарий;
- ошибки и восстановление после сбоя проверены;
- документация обновлена;
- данные старой версии не потеряны;
- изменения локальны и воспроизводимы через Docker/lockfiles;
- заказчику предоставлен проверяемый результат;
- следующий этап не начат автоматически.
